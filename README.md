## Модульные (unit) тесты
* Если полученные данные от фронта не являются корректным json-ом, то тестируемый метод возвращает 400 с сообщением об ошибке "Переданный формат данных некорректен"
* Если в переданном JSON отсутствует одно из обязательных полей (card_number, card_holder, card_expiration, cvv, order_number, sum), то тестируемый метод возвращает 400 с сообщением об ошибке "«"Отсутствует обязательное поле"

* Если card_number содержит что-то, кроме цифр, то тестируемый метод возвращает 400 с сообщением об ошибке "Номер карты некорректен"
* Если card_number содержит не ровно 16 цифр, то тестируемый метод возвращает 400 с сообщением об ошибке "Номер карты некорректен"

* Если card_holder содержит что-то, кроме латинских букв A-Za-z, дефиса и пробела, то тестируемый метод возвращает 400 с сообщением об ошибке "Владелец карты некорректен"
* Если card_holder пустой, то тестируемый метод возвращает 400 с сообщением об ошибке "Владелец карты некорректен"
* Если в card_holder часть имени или фамилии содержит дефис в начале или конце (например, "-John"), то тестируемый метод возвращает 400 с сообщением об ошибке "«"Владелец карты некорректен"

* Если card_expiration не соответствует формату даты мм/гг, то тестируемый метод возвращает 400 с сообщением об ошибке "Срок окончания действия карты некорректен"
* Если card_expiration содержит некорректную дату, например 31/26, то тестируемый метод возвращает 400 с сообщением об ошибке "Срок окончания действия карты некорректен"
* Если card_expiration содержит просроченную дату, то тестируемый метод возвращает 400 с сообщением об ошибке "Срок окончания действия карты некорректен"

* Если cvv содержит что-то, кроме цифр, то тестируемый метод возвращает 400 с сообщением об ошибке "CVV код некорректен"
* Если cvv содержит не ровно 3 цифры, то тестируемый метод возвращает 400 с сообщением об ошибке "CVV код некорректен"

* Если order_number пустой, то тестируемый метод возвращает 400 с сообщением об ошибке "Номер заказа некорректен"
* Если order_number содержит более 16 символов, то тестируемый метод возвращает 400 с сообщением об ошибке "Номер заказа некорректен"

* Если sum пустой или равен 0 (здесь учитываем все возможные вариации, типа 0; 0,0; 0,00 и др.), то тестируемый метод возвращает 400 с сообщением об ошибке "Сумма оплаты некорректна"
* Если sum содержит что-то, кроме цифр 0-9 и запятой, причем запятая не должна быть первым символом, то тестируемый метод возвращает 400 с сообщением об ошибке "Сумма оплаты некорректна"
* Если sum содержит больше 2 знаков после запятой (возможно, может быть больше, нужно уточнять у заказчика), то тестируемый метод возвращает 400 с сообщением об ошибке "Сумма оплаты некорректна"
* Если sum содержит более одной запятой (например, "1,00,0"), то возвращается 400 с сообщением "Сумма оплаты некорректна"
* Если в sum перед запятой нет цифр (например, ",50"), то возвращается 400 с сообщением "«"Сумма оплаты некорректна"

* **Успешный сценарий:** Если все значения корректны, то тестируемый метод возвращает true.

### Проверяем связку «бэк-сервис А»
* Если сервис A недоступен или возвращает пустой ответ или какие-то другие коды, кроме 403 и 200, то бэк возвращает 400 с сообщением об ошибке "Ошибка платежного сервиса, повторите попытку позже"
* Если сервис A возвращает HTTP-код 403, то бэк возвращает 403 с сообщением об ошибке
* **Успешный сценарий:** Если сервис А вернул 200, то на бэке далее должен вызываться следующий метод, бэк не возвращает никакую ошибку.

### Проверяем связку «бэк-репозиторий»
* Если метод репозитория setOrderIsPaid ничего не возвращает, то бэк возвращает 400 с сообщением об ошибке
* Если метод репозитория setOrderIsPaid возвращает исключение, то бэк возвращает 400 с сообщением об ошибке
* **Успешный сценарий:** Если метод репозитория setOrderIsPaid успешно выполнен (вернул true), то бэк возвращает 200 с сообщением об успехе

## Системные тесты
* Если cvv неверен, то после получения ответа от бэка на фронте выводится сообщение об ошибке «Не удалось списать данные с карты, проверьте реквизиты». Запись в БД об успешной оплате отсутствует.
* Если номер карты неверен, то после получения ответа от бэка на фронте выводится сообщение об ошибке «Не удалось списать данные с карты, проверьте реквизиты». Запись в БД об успешной оплате отсутствует.
* Если на карте, данные от которой были введены недостаточно средств, то на фронте выводится сообщение «Не удалось списать данные с карты, проверьте реквизиты». Запись в БД об успешной оплате отсутствует.
* **Успешный сценарий:** Если все введенные данные карты корректны (номер, держатель, срок, CVV), система списывает средства, записывает оплату в БД (в БД появляется запись с соответствующим номером заказа и суммой), на фронте выводится сообщение «Оплата прошла успешно».

## Способы удешевления тестирования
* Использование тестовых карт или тестового платежного сервиса А. Большинство платёжных провайдеров предоставляют тестовую среду, где все операции имитируются без реального списания средств.

* Мокирование (mocking) внешнего сервиса на уровнях модульного и интеграционного тестирования. Вместо реальных вызовов к сервису А использовать заглушки, которые возвращают предопределённые ответы (200, 403, 500).

Выше приведены способы удешевления тестирования только в плане реальных денежных затрат при тестировании оплаты. Если эе говорить в принципе про удешевление тестирования, то с этам может помочь автоматизация тестирования и их регулярный прогон в CI/CD.
