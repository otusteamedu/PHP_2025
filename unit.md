1. Модульные тесты:

Валидация входных данных:
общий кейс:
+ в запросе переданы верные параметры, подходящие под валидацию -> ответ 200

card_number:
- в запросе нет поля card_number, остальные поля есть и валидные -> ответ 400 с сообщением об ошибке
- в запросе передан пустой card_number, остальные поля есть и валидные -> ответ 400 с сообщением об ошибке
- в запросе передан некорректный card_number (не состоит из цифр и/или имеет лишние символы), остальные поля есть и валидные -> ответ 400 с сообщением об ошибке
- в запросе передан некорректный card_number (более 16 цифр), остальные поля есть и валидные -> ответ 400 с сообщением об ошибке
- в запросе передан некорректный card_number (менее 16 цифр), остальные поля есть и валидные -> ответ 400 с сообщением об ошибке

card_holder:
- в запросе нет поля card_holder, остальные поля есть и валидные -> ответ 400 с сообщением об ошибке
- в запросе передан пустой card_holder, остальные поля есть и валидные -> ответ 400 с сообщением об ошибке
- в запросе передан некорректный card_holder (есть символы кроме латиницы/дефиса/пробела), остальные поля есть и валидные -> ответ 400 с сообщением об ошибке
- в запросе передан некорректный card_holder (имеет более одного пробела), остальные поля есть и валидные -> ответ 400 с сообщением об ошибке

card_expiration:
- в запросе нет поля card_expiration, остальные поля есть и валидные -> ответ 400 с сообщением об ошибке
- в запросе передан пустой card_expiration, остальные поля есть и валидные -> ответ 400 с сообщением об ошибке
- в запросе передан некорректный card_expiration (формат отличается от мм/гг), остальные поля есть и валидные -> ответ 400 с сообщением об ошибке
- в запросе передан некорректный card_expiration (содержит не валидный месяц и/или год), остальные поля есть и валидные -> ответ 400 с сообщением об ошибке

cvv:
- в запросе нет поля cvv, остальные поля есть и валидные -> ответ 400 с сообщением об ошибке
- в запросе передан пустой cvv, остальные поля есть и валидные -> ответ 400 с сообщением об ошибке
- в запросе передан некорректный cvv (не состоит из цифр и/или имеет лишние символы), остальные поля есть и валидные -> ответ 400 с сообщением об ошибке
- в запросе передан некорректный cvv (более 3 цифр), остальные поля есть и валидные -> ответ 400 с сообщением об ошибке
- в запросе передан некорректный cvv (менее 3 цифр), остальные поля есть и валидные -> ответ 400 с сообщением об ошибке

order_number:
- в запросе нет поля order_number, остальные поля есть и валидные -> ответ 400 с сообщением об ошибке
- в запросе передан пустой order_number, остальные поля есть и валидные -> ответ 400 с сообщением об ошибке
- в запросе передан некорректный order_number (не проходит валидацию в зависимости от выбранного формата номера (например: uuid, int и тп)), остальные поля есть и валидные -> ответ 400 с сообщением об ошибке
- в запросе передан некорректный order_number (более 16 цифр), остальные поля есть и валидные -> ответ 400 с сообщением об ошибке

sum:
- в запросе нет поля sum, остальные поля есть и валидные -> ответ 400 с сообщением об ошибке
- в запросе передан пустой sum, остальные поля есть и валидные -> ответ 400 с сообщением об ошибке
- в запросе передан некорректный sum (не проходит валидацию с форматом суммы через ,), остальные поля есть и валидные -> ответ 400 с сообщением об ошибке
- в запросе передан некорректный sum (меньше или равно 0), остальные поля есть и валидные -> ответ 400 с сообщением об ошибке

2. Интеграционные тесты:
Проверяем связку «фронт-бэк»:
- если пришла ошибка на card_number (кейсы описаны в п.1), фронт подсвечивает это поле красным цветом
- если пришла ошибка на card_holder (кейсы описаны в п.1), фронт подсвечивает это поле красным цветом
- если пришла ошибка на card_expiration (кейсы описаны в п.1), фронт подсвечивает это поле красным цветом
- если пришла ошибка на cvv (кейсы описаны в п.1), фронт подсвечивает это поле красным цветом
- если пришла ошибка на sum (кейсы описаны в п.1), фронт подсвечивает это поле красным цветом
+ если все поля корректные, фронт показывает успешное сообщение/модалку/...

Проверяем связку «бэк-сервис А»:
- если сервис А ответил 403 -> ответ 403 с сообщением об ошибке
- если сервис А ответил любым кодом кроме 403 и 200 -> ответ 500 с сообщением об ошибке
+ если сервис А ответил 200 -> ответ 200

Проверяем связку «бэк-репозиторий»:
+ если метод setOrderIsPaid возвращает true -> ответ 200 (дополнительно можно проверить, что запись появилась/обновилась в базе)
- если метод setOrderIsPaid возвращает общее исключение (некорректный номер заказа/сумма) -> ответ 400 с сообщением об ошибке
- если метод setOrderIsPaid возвращает критичное исключение (не удалось подключиться к бд) -> ответ 500 с сообщением об ошибке

3. Системные тесты:
- если какой то из параметров не валидный, то после получения ответа от бэка на фронте выводится сообщение об ошибке и нужное поле подсветилось красным
- если сервис А ответил ошибкой, фронт выводит сообщение о неуспешной попытке оплаты
- если метод setOrderIsPaid ответил ошибкой, фронт выводит сообщение о неуспешной попытке оплаты + кнопка для обращения в саппорт
+ если все поля валидные, сервис А ответил 200 и setOrderIsPaid вернул true, фронт выводит сообщение об успешной оплате

Удешевление тестирования:
- проверка сервиса А через мок запросов-ответов, либо через тестовое окружение сервиса А
- запуск тестов на отдельной бд, чтобы было меньше данных и не было шанса зааффектить юзеров
